## Ops / auth notes (NOT server bugs — environment)
### ISSUE 1 — os_recommend_flavor always empty on Rackspace IAD3 (regression)
- Symptom: `os_recommend_flavor(workload="web app")` and `workload="database"` both return `recommendations:[]` + "No flavors match the specified requirements" while `total_available:20`.
- Root cause: `ComputeService.listFlavors` (Sources/OpenStackClient/Services/ComputeService.swift:321) calls `GET {base}/flavors` (NON-detail). On Rackspace IAD3, plain `/flavors` returns only `{id,name,links}` — NO vcpus/ram/disk. Specs exist only at `/flavors/detail`. So every decoded Flavor has `vcpus=nil`, `ram=nil`; the recommender's `guard let vcpus = f.vcpus, let ramMb = f.ram else { continue }` (FlavorRecommendationHandler.swift:43) skips ALL 20 → zero recommendations.
- Verified live: `GET /v2.1/flavors?os-region-name=IAD3` → first flavor keys `[id, links, name]`; `GET /v2.1/flavors/detail?os-region-name=IAD3` → first flavor `{name,vcpus:4,ram:16384,disk:80}`.
- Impact: breaks A6 (RAM-favored rec), A7 (quantum fallback), A8 (min_ram filter) in Part A smoke, plus `os_project_readiness` — its embedded `flavors.items[]` ALL show `vcpus:0 ram:0 disk:0` on IAD3 (same bare /flavors source), so the readiness surface silently reports zero specs for every flavor. Whole non-expert flavor-discovery UX broken on any cloud whose bare /flavors omits specs (Rackspace). Not caught because unit tests use FakeOpenStack which populates full spec objects regardless of path.
- Fix direction: point `listFlavors` at `/flavors/detail` (standard OpenStack detail endpoint, what most clouds serve by default) OR enrich each listed flavor via getFlavorExtraSpecs-style fetch. Prefer switching to `/flavors/detail` (single call, correct semantics); keep per-flavor extra_specs enrichment get-only. Both `os_recommend_flavor` and `os_project_readiness` read from listFlavors, so this one fix repairs both.
### ISSUE 2 — os_quota(network) 403 policy denial shows misleading "quota exceeded" Hint
- Symptom: `os_quota(service="network")` → HTTP 403 PolicyNotAuthorized ("rule:get_quota is disallowed by policy"), but the appended Hint says "Quota exceeded. Delete unused resources or request a quota increase from your cloud provider."
- Root cause: the generic 403→quota hint mapping treats any 403 as quota exhaustion; a Keystone/Neutron *policy* denial (get_quota disallowed for member role) is not a quota problem.
- Impact: low-severity — misdirects a non-expert toward deleting things instead of raising privileges. compute/volume quotas work fine on IAD3 (compute: instances=100 cores=200 ram=512000MB keypairs=100; volume: volumes=10 GB=1000 snapshots=10).
- Fix direction: reserve the "quota exceeded" hint for explicit quota error codes (e.g. over-quota message / Os-QUOTA); a `PolicyNotAuthorized` 403 should map to an auth/privilege hint ("this operation requires elevated rights; your role cannot read network quotas").
